## Ef core performance tuning

| Tuning | Description |
|--|--|
| DbContext pooling | У реєстрації DbContext в DI є набір з декількох перевантажень: перше це звичайна реєстрація; друге реєстрація з пулінгом DbContext. Дефолтний DbContext має lifetime як Scoped, створюється на кожен запит, відповідно багато запитів = багато аллокацій = великий memory usage = натиск на GC. Пулінг використовує DbContext як Singleton і перед поверненням в пул очищає повністю його стан, за замовчування розмір пулу 1024, його можна корегувати. Якщо rps великий, усі DbContext-и з пулу задіяні, тоді поведінка для нових DbContext стає дефолтною як Scoped. Якщо в час піку навантаження кількість контекстів умовно = 900, а з часом rps спав до 10 контекстів, решта 890 контекстів не знищується і живуть далі, вони продовжують жити в памяті і  утримують connection + не роблять нічого корисного. Тому тут ситуація з компромісами. |
| Compiled queries | Пропускають частину пайплайну виконання sql statement, комілюються під час сетапу і далі живуть у памяті. Використовувати для повторних запитів з дуже простою структурою і без ніяких динамічних виразів. |
| Query caching and parameterization | Тут треба розуміти, що ef core кешує лише запити з ідентичною структурою, у вираз передавати замість фактичних значень лише змінну, щоб досягти структурної параметризації + інтрументарій кешування. |
| Projection via select | Під час побудови запиту через linq, вибирати прямо в цей момент усі необхідні дані, щоб не тягнути взагалі непотрібні. Можна мапити модель в dto зразу під час Select в дереві виразів.|
| Сartesian explosion and assplitquerys | Запити з великою кількістю інклудів, які потім транслюються у багато джоінів, розбивати на малі запити через AsSplitQuery, оскільки під час багатьох джоінів можна випадково отримати набагато більше запитів ніж ми очікуємо. Якщо актуальність даних важлива, обгортати в транзакцію з достатнім рівнем. Тільки замість AsNoTracking прийдеться використовувати AsNoTrackingWithIdentityResolution. |
| !nvarchar(max) for all strings | За замовчуванням ef core ставить усім рядкам nvarchar(max), це = більше памяті. У Npgsql поведінка трішки інша, там string мапиться як text/varchar(n), продуктивність взагалі не падає. Я особисто завжди віддаю перевагу вказувати максимальну довжину явним чином через MaxLength.  |
| ExecuteDelete + ExecuteUpdate | Запити в циклах це анти практика, багато компіляцій запитів, використовувати для таких випадків спеціальни методи від ef core. |
| Batching | Під час декількох команд у межах одного SaveChanges, згенеровані запити відправляються разом, потрібно, щоб не відправляти по одому запиту, типу як вирішення network issues. У MaxBatchSize визначається скільких таких запитів може відправитися однією пачкою. Ну ось як приклад, якщо ми в методі створимо 150 нових entities, а MaxBatchSize умовно = 42, ef core розібє на ≈4 пачки для відправки запитів.  |
